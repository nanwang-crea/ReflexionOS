# ReflexionOS 多会话并行需求规范

## 1. 背景

当前项目的数据模型和后端接口已经具备多会话基础能力：

- 后端以 `session_id` 作为会话隔离主键，已有创建、列举、更新、删除接口。
- 对话快照、事件流、消息、turn、run 都按 `session_id` 归属。
- WebSocket 连接也是按 `session_id` 建立。
- 前端 `conversation.store` 已按 `sessionId` 缓存多份会话状态。

但当前前端工作区仍然是“单激活会话运行时”模型：

- `workspace.store` 只有一个 `currentSessionId`。
- `useConversationRuntime(currentSessionId)` 只维护当前选中会话的一条运行时连接。
- 用户在会话 A 运行中切换到会话 B 时，A 虽然会在后端继续执行，但前端对 A 的状态感知、列表提示、后台更新和未读判定都不完整。

因此，当前系统具备“多会话数据存在”的能力，但还不具备“多会话并行可用体验”。

## 2. 目标

新增多会话并行能力，使用户可以在一个会话执行过程中切换到其他会话继续查看、创建、发送和等待结果，而不必停留在当前运行中的会话页面。

本期目标：

- 支持运行中切换会话。
- 支持不同会话各自独立运行。
- 支持切回后看到正确状态和结果。
- 支持在会话列表中识别哪些会话正在运行、等待审批、产生了新内容。
- 明确后台同步策略、未读基线、性能上限和失败降级规则。

## 3. 非目标

本需求明确不包含以下能力：

- 同一会话内同时运行多个 turn / run。
- 同一条用户消息分叉出多个并行回答。
- 多窗口协同编辑同一会话。
- 跨设备实时同步。
- 会话级资源配额、优先级调度、抢占执行。

说明：
“多会话并行”指的是不同 `session` 之间可以并行，不是同一个 `session` 内多 run 并行。现有后端约束保持不变：每个 `session` 最多一个 `active_turn_id`。

## 4. 用户故事

### 4.1 运行中切换

作为用户，我在会话 A 提交任务后，希望立即切换到会话 B，而不是被迫停留在 A 的页面等待执行结束。

### 4.2 后台继续运行

作为用户，我切到其他会话后，希望会话 A 继续在后台运行，不因为切换页面而中断。

### 4.3 多会话独立执行

作为用户，我希望会话 A 正在运行时，仍然可以在会话 B 发起新的任务，只要 B 自己没有正在运行的任务。

### 4.4 列表可见状态

作为用户，我希望在侧边栏会话列表里一眼看出哪些会话正在运行、哪些在等待审批、哪些已经有新回复但我还没看。

### 4.5 切回即恢复

作为用户，我切回某个运行中的会话时，希望立即看到最新 transcript、当前 run 状态、审批卡片、计划面板和工具执行结果，而不是丢状态或必须手动刷新。

## 5. 产品定义

### 5.1 会话并行的定义

这里列举的是“某个会话的 active run 所处状态”，不是 `session` 模型自身的状态字段。

系统支持多个不同 `session` 的 active run 同时处于以下任一非终态：

- `created`
- `running`
- `waiting_for_approval`
- `resuming`

每个 `session` 在任意时刻仍只允许一个 active run。

状态真值来源：

- `created` / `running` / `waiting_for_approval` / `resuming` / `completed` / `failed` / `cancelled` 直接来自现有 `ConversationRunStatus`。
- `resuming` 的真值来源是后端 run 状态和事件 `run.resuming`，前端不得自行杜撰该状态。
- `pending` 虽然在前端类型声明中存在，但当前实现没有任何状态转移或事件会产生它；本期需求不将其视为现状能力，也不要求实现相关分支。

### 5.2 切换的定义

“切换会话”指用户修改 `currentSessionId`，使工作区主视图从会话 A 的 `transcript / input / header` 切换为会话 B 的 `transcript / input / header`。

切换动作本身不应：

- 取消原会话 run。
- 清空原会话缓存。
- 关闭后端执行任务。
- 丢失原会话的待审批状态。

### 5.3 后台保持运行的定义

当用户离开当前会话时，原会话若已发起 run，则该 run 应继续执行直到：

- 正常完成。
- 失败。
- 被用户取消。
- 因审批等待而暂停。

“后台保持运行”是执行连续性要求，不要求后台会话始终渲染完整 UI，但要求状态最终一致，并且前端能感知其关键变化。

## 6. 功能需求

### 6.1 会话切换

系统必须允许用户在以下状态下切换到其他会话：

- 当前会话正在流式输出。
- 当前会话正在调用工具。
- 当前会话等待审批。
- 当前会话取消中。

切换后：

- 工作区主视图展示新选中会话内容。
- 原会话继续执行。
- 输入框和取消按钮必须绑定到当前选中会话，而不是上一个会话。

### 6.2 会话列表状态展示

侧边栏会话项至少需要支持以下展示状态：

- `running`
- `waiting_for_approval`
- `completed_with_unread_activity`
- `failed_with_unread_activity`
- `idle`

这些展示状态不是后端原生字段，而是由会话派生字段计算得出。映射规则必须统一：

- `waiting_for_approval`: `hasPendingApproval = true`
- `running`: `hasActiveRun = true` 且 `activeRunStatus` 属于 `created | running | resuming`
- `failed_with_unread_activity`: 最近一次终态 run 为 `failed` 且 `hasUnreadActivity = true`
- `completed_with_unread_activity`: 最近一次新活动来自 assistant、tool 或 run 终态变化，且 `hasUnreadActivity = true`，并且不属于 `failed_with_unread_activity`
- `idle`: 以上条件均不满足

最低可接受展示形式：

- 状态点、badge、文案任一即可。
- 必须能区分“正在跑”和“等待审批”。
- 必须能区分“有新内容但当前未查看”。

### 6.3 后台会话同步策略

本期明确采用以下策略，不再保留多种实现路线：

- 当前选中会话始终维持实时 WebSocket 连接。
- 非当前会话中，处于 `created / running / waiting_for_approval / resuming` 的会话，也维持后台实时连接。
- 已进入终态 `completed / failed / cancelled` 的非当前会话，允许断开实时连接，仅保留缓存摘要状态。

连接管理规则：

- 前端需要从“单连接模型”升级为“按 `sessionId` 管理多连接”模型。
- 同时维持后台实时同步的会话数量上限为 `5`。
- 当非当前活跃会话数超过 `5` 时，优先级最低的会话降级为“无常驻连接，只在重新进入或显式刷新时补拉快照”。

优先级规则：

- 当前选中会话优先级最高。
- `waiting_for_approval` 高于普通 `running`。
- 最近活动时间更近的会话优先。

说明：
该优先级用于连接分配。侧边栏显示排序见第 8.1 节，两者必须保持一致，不允许只修改一处。

降级后的最低保证：

- 该会话重新进入时必须立即补拉最新快照。
- 应用刷新恢复后必须补拉其正确终态。
- 不要求降级会话保持逐 token 实时流式细节。

### 6.4 多会话发起执行

当会话 A 正在运行时，用户可以在会话 B 发起新一轮对话，前提是：

- 会话 B 当前没有 active run。
- 当前项目、模型配置、输入校验均满足现有发送条件。

系统不得因为会话 A 正在运行，就全局禁用其他会话发送。

### 6.5 当前会话操作绑定

下列操作必须严格作用于当前会话，不得串会话：

- 发送消息
- 取消运行
- 审批通过
- 审批拒绝
- 信任授权
- 编辑并重跑
- 切换 agent mode
- 上传附件

### 6.6 未读活动

未读活动必须按 `last_seen_event_seq` 与 `session.last_event_seq` 的差值判定，不得只依赖时间戳或临时 UI 标志。

定义：

- `last_seen_event_seq`: 用户最后一次“成功进入该会话并完成最新快照同步”时记录的事件序号。
- `hasUnreadActivity = session.last_event_seq > last_seen_event_seq`

存储要求：

- `last_seen_event_seq` 存在前端持久化层，和 `workspace` 级 UI 状态一起持久化。
- 本期不要求后端持久化该字段。

标记规则：

- 当用户不在会话 A 中，而 A 的 `last_event_seq` 增长时，A 进入“有新活动”状态。
- 用户重新进入该会话，且完成最新快照同步后，将 `last_seen_event_seq` 更新为该会话当前 `last_event_seq`，清除未读标记。

### 6.7 等待审批场景

若某后台会话进入 `waiting_for_approval`：

- 会话列表必须出现明显提示。
- 该会话应提升后台连接优先级。
- 用户切回该会话后应能看到完整审批卡片。
- 审批动作必须仍然可以正常恢复对应 run。

若同时有多个后台会话进入 `waiting_for_approval`：

- 列表中统一以 `waiting_for_approval` 状态展示。
- 排序优先级高于普通运行中会话。
- 多个待审批会话之间按最近活动时间倒序排列。

本期不强制要求“跨会话直接在侧边栏审批”，但必须保证能快速定位到待审批会话。

### 6.8 取消场景

若用户在会话 A 发起取消后立即切到会话 B：

- A 的取消过程继续完成。
- A 的最终状态在列表和会话详情中一致。
- 不得因为视图切走导致取消悬空。

### 6.9 新建会话

运行中的旧会话不应阻止用户：

- 新建空会话
- 新建后直接发送第一条消息
- 切回已有其他会话

## 7. 状态模型要求

### 7.1 会话级派生状态

前端需要能够为每个会话派生一个轻量级 sidebar/runtime 状态，至少包含：

- `hasActiveRun`
- `activeRunStatus`
- `hasPendingApproval`
- `lastActivityAt`
- `hasUnreadActivity`
- `lastSeenEventSeq`
- `sidebarStatus`

`lastAssistantMessagePreview` 本期不作为必做项，不纳入验收标准。如果后续需要做列表摘要，可基于现有派生状态扩展。

### 7.2 真值来源

状态真值来源要求如下：

- 对话正文、run、turn、message 真值来自会话快照或事件流。
- `currentSessionId` 真值来自 `workspace.currentSessionId`。
- `lastSeenEventSeq` 真值来自前端持久化状态。
- `hasUnreadActivity` 由 `last_event_seq > lastSeenEventSeq` 派生。
- `sidebarStatus` 由 `hasActiveRun / activeRunStatus / hasPendingApproval / hasUnreadActivity` 派生，不得另存一份独立真值。

### 7.3 一致性要求

任意会话切换、重连、刷新页面后，系统应能恢复：

- 当前选中会话
- 每个会话最近一次已知运行状态
- 已缓存会话 transcript
- 待审批状态
- 每个会话的 `lastSeenEventSeq`
- 每个会话的未读状态

其中：

- run / turn / message 真值以服务端快照和事件为准。
- 未读状态以本地 `lastSeenEventSeq` 重新计算为准。

## 8. 交互规范

### 8.1 侧边栏

侧边栏会话列表应支持：

- 点击切换当前会话
- 显示当前激活会话
- 显示运行中 / 等待审批 / 未读状态
- 运行中会话排序策略保持稳定，不因短暂事件频繁跳位

本期排序规则：

- 第一优先级：`waiting_for_approval`
- 第二优先级：`running / resuming / created`
- 第三优先级：最近活动时间倒序
- 同优先级内保持稳定排序，不因逐 token 流式事件导致反复重排

说明：
该排序优先级应与第 6.3 节的连接分配优先级保持一致。

### 8.2 工作区主视图

工作区只展示一个当前会话的详细内容，但必须支持快速切换。

切换时：

- 不展示前一个会话的流式残留内容。
- 不出现“取消按钮控制了别的会话”的错绑。
- transcript 滚动位置按会话分别记忆为佳；若本期不做，也不能出现错乱复用。

### 8.3 输入区

输入区规则：

- 当前选中会话若正在运行，则输入区对该会话保持现有禁用 / 取消逻辑。
- 切到另一个空闲会话时，输入区应恢复可发送。
- 输入区附件队列必须与当前会话绑定，不得跨会话残留。

### 8.4 提示反馈

用户需要收到以下提示：

- 切换到后台仍在运行的会话时，允许以轻量方式提示“该会话仍在运行”。
- 某个后台会话进入 `waiting_for_approval` 时，应有显式提示，形式可以是 toast + sidebar badge。
- 某个后台会话失败时，应有一次性失败提示，形式可以是 toast 或明显列表状态变化。
- 某个后台会话完成时，不强制 toast，但必须有未读状态或完成状态可见。

提示协调规则：

- 对非当前会话，不要求展示全文实时流式内容。
- 但关键状态变化必须通过 sidebar 状态和必要 toast 可见。
- 同一后台会话的同一失败事件不得重复 toast 轰炸。

## 9. 约束与兼容性

### 9.1 保持现有后端约束

本需求不改变以下现有规则：

- 一个 `session` 只能有一个 `active_turn_id`
- 取消、审批、重跑等操作仍按会话和 run 精确定位
- conversation snapshot / event 模型不改语义

### 9.2 性能约束

多会话并行不能明显恶化前端性能。本期量化约束如下：

- 同时维持实时后台同步的会话数上限为 `5`
- transcript 只渲染当前会话
- 非当前会话只维护摘要状态，不做完整 transcript 重渲染
- 单个非当前会话的逐 token 流式更新不得触发整个 sidebar 高频重排

超过上限时：

- 超出的活跃会话降级为“切回补拉快照”
- 降级不影响当前会话和待审批会话

### 9.3 重连与恢复

若 WebSocket 中断或应用刷新：

- 已在运行的会话不能因此被视为终止。
- 前端恢复后应重新建立允许范围内的活跃会话连接。
- 若后台会话在离线期间完成，恢复后列表和详情都应显示终态。

若后台会话重连失败：

- 该会话标记为“同步异常”但不改变 run 业务状态。
- 前端进入快照补拉降级模式。
- 用户重新进入该会话时必须强制补拉快照。

## 10. 验收标准

### 10.1 基础切换

- 会话 A 运行中时，用户可以点击进入会话 B。
- 切换后 UI 无卡死、无报错、无错绑按钮。
- 会话 A 在后端继续执行。

### 10.2 并行执行

- 会话 A 运行中时，用户可在会话 B 发起新 run。
- A、B 均可独立完成。
- 两个会话结果互不串写。

### 10.3 状态可见

- 侧边栏可准确显示 A、B 哪个在运行、哪个等待审批、哪个已完成并有未读。
- 后台完成的会话能被标记为有新活动。
- 同时多个待审批会话时，列表排序符合本规范。

### 10.4 切回恢复

- 用户切回会话 A 时，能看到最新 transcript、run 状态、审批卡片和计划状态。
- 不需要手动刷新浏览器。

### 10.5 同会话限制不变

- 在同一个会话已存在 active run 时，仍不能再发起第二个 run。
- 错误提示清晰，且不影响其他会话发送。

### 10.6 刷新恢复

- 应用刷新后，当前选中会话恢复正常。
- 正在运行或等待审批的会话能够重新同步到正确状态。
- 未读状态按 `lastSeenEventSeq` 正确恢复。

### 10.7 性能与降级

- 活跃后台连接数不超过 `5`
- 超过 `5` 时，低优先级会话正确降级为补拉模式
- 被降级会话在重新进入时能恢复正确状态

## 11. 实现边界建议

为避免范围失控，建议第一阶段落地下列最小闭环：

- 用户可在会话运行中切换到其他会话
- 不同会话可各自独立运行
- 侧边栏显示运行中 / 等待审批 / 未读活动
- 切回会话可恢复正确详情
- 活跃会话采用多连接管理，非活跃终态会话断开连接

第一阶段不强求：

- 所有后台会话的全文实时流式渲染
- 复杂通知中心
- 会话级执行队列管理
- 拖拽排序 / pin / 分组等会话管理增强
- 会话列表摘要预览

## 12. 风险点

需要重点防止以下问题：

- 运行时连接只跟随 `currentSessionId`，导致后台会话状态长期不更新
- 多连接后操作绑定混乱，取消、审批、重跑误作用到错误会话
- 附件队列、输入内容、滚动状态跨会话串用
- sidebar 只看当前会话状态，无法反映其他运行中的会话
- 页面刷新后后台运行状态丢失
- 未读基线只靠时间戳或 toast，刷新后行为不稳定
- 多个后台失败 / 待审批同时出现时，提示风暴或排序混乱

## 13. 需求结论

这次需求的本质不是“新增会话模型”，而是把项目当前已经存在的 `session` 隔离能力，补齐成一个真正可用的多会话并行产品体验。

一句话定义：

用户可以让多个不同会话各自独立运行，并在运行过程中自由切换查看和继续操作其他会话，而系统始终保持状态正确、不串会话、可见可恢复。
