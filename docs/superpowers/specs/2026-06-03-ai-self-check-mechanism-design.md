# AI 自检机制设计（Self-Check Mechanism）

## 问题

AI Agent 在执行任务时，可能出现：
- 偏离用户目标（目的漂移）
- 对操作对象理解有误（猜测代替读取）
- 选择不可行的执行路径（盲目行动）
- 修改范围不可控（意外破坏）

当前系统缺少一个结构化的"行动前自检"环节，导致错误操作只有在执行后才被发现。

## 设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 自检触发时机 | 关键节点触发（非每步必检） | 纯只读操作无外部影响，跳过可降低开销 |
| 自检项数量 | 4 项 | 覆盖目的/理解/路径/副作用，不多不少 |
| 每项评估级别 | 3 级（低/中/高） | 简单明确，避免模糊的数值评分 |
| 置信度判定规则 | 按低/中项数量判定 | 规则清晰，无需加权计算 |
| 中置信度行为 | 微暂停（自我澄清+继续） | 不打断流程，但留下审计痕迹 |
| 低置信度行为 | 暂停等人决策 | 涉及不可逆操作时必须有人把关 |
| 低置信度交互上限 | 2 轮 | 防止无限循环，2 轮后无法继续 |
| 2 轮后仍低 | 输出"无法继续"+状态报告 | 不自动回退（回退本身也有风险），把状态摆出来让人判断 |

---

## 一、四项自检内容与评估标准

每次触发自检时，AI 检查以下四项：

### ① 目的对齐 — "我当前这一步，是在完成用户要求的任务吗？"

| 级别 | 判定条件 | 示例 |
|------|----------|------|
| **高** | 当前操作与用户原始请求直接对应，无偏移 | 用户要求"修复登录 bug"，当前正在修改登录函数 |
| **中** | 当前操作与目标间接相关，但中间推断步骤较多 | 用户要求"优化性能"，当前在分析日志格式（间接但必要） |
| **低** | 当前操作偏离用户目标，或无法解释与目标的关系 | 用户要求"修复登录 bug"，当前在重构整个项目结构 |

### ② 理解确认 — "我对当前操作对象的理解正确吗？"

| 级别 | 判定条件 | 示例 |
|------|----------|------|
| **高** | 基于完整读取/搜索结果理解，无猜测成分 | 已读取目标文件全文，确认函数签名和调用关系 |
| **中** | 基于部分证据理解，有合理推断但未完全验证 | 读了文件开头 50 行，基于命名推断后续逻辑 |
| **低** | 有明显猜测成分，未读取关键信息就行动 | 没读过文件，凭文件名猜测内容并直接修改 |

### ③ 路径可行 — "我选择的执行路径能达成目的吗？"

| 级别 | 判定条件 | 示例 |
|------|----------|------|
| **高** | 路径清晰，无前置障碍，步骤可直接执行 | 修改单个函数，依赖已确认存在 |
| **中** | 路径基本可行，但需要前置条件或存在可解决的障碍 | 需要先安装依赖包，或需修改 2 个相关文件 |
| **低** | 路径有明显障碍，或根本无法达成目的 | 目标 API 不存在，或需要修改编译后的二进制文件 |

### ④ 副作用可控 — "这一步的修改范围是否可控，不会引发意外破坏？"

| 级别 | 判定条件 | 示例 |
|------|----------|------|
| **高** | 修改范围精确可控，影响仅限于目标 | 修改单个函数内部逻辑，无调用方受影响 |
| **中** | 修改范围已知但较大，可能影响相关模块 | 修改公共接口签名，需同步更新 3 个调用方 |
| **低** | 可能波及未知范围，无法评估影响 | 修改全局配置文件，不确定哪些模块依赖此配置 |

## 二、置信度综合判定规则

四项评估的综合结果决定置信度级别：

```
┌─────────────────────────────────┬──────────┐
│ 条件                            │ 置信度    │
├─────────────────────────────────┼──────────┤
│ 四项全部为"高"                  │ 高       │
│ 恰好 1 项为"中"或"低"           │ 中       │
│ 2 项及以上为"中"或"低"          │ 低       │
└─────────────────────────────────┴──────────┘
```

---

## 三、分支执行流程

### 高置信度 → 直接执行

四项全部为高，AI 直接执行操作，无需额外说明。

### 中置信度 → 微暂停

AI 自我澄清后继续执行，**不需等人确认**。

**具体行为：**
1. AI 在输出中简短说明不确定项
2. 说明不确定的原因
3. 说明继续执行的依据
4. 继续执行

**输出模板：**
```
[自检·微暂停] 我对「{不确定项}」有部分不确定，因为{原因}，但基于{依据}继续执行。
```

**示例：**
```
[自检·微暂停] 我对「理解确认」有部分不确定，因为只读取了文件前50行，
但基于函数命名规范和已有测试用例继续执行。
```

### 低置信度 → 暂停等人

2 项及以上为中/低，AI 暂停执行，向人呈现自检结果并请求决策。

**输出模板：**
```
[自检·暂停] 置信度不足，请决策：

自检结果：
- 目的对齐：{级别} — {简述}
- 理解确认：{级别} — {简述}
- 路径可行：{级别} — {简述}
- 副作用可控：{级别} — {简述}

请选择：
1. 继续 — 按当前理解执行
2. 换路径 — 指定新方向（至少给一个关键词/提示）
3. 补充信息 — 提供具体信息帮助我重新评估
```

---

## 四、低置信度交互的决策分支

人做出决策后，AI 按以下分支处理：

### 分支 1：人选择"继续"

- AI 按当前理解执行
- 标记此步骤为"人授权·低置信度"
- 后续若出问题，可追溯到此决策点

### 分支 2：人选择"换路径"

- 人需指定新方向（至少给一个关键词/提示）
- AI 重新执行四项自检，置信度重新评估
- 若仍为低置信度，再次暂停（计入轮次上限）

### 分支 3：人选择"补充信息"

- 人提供具体信息（文档片段、代码位置、需求澄清等）
- AI 吸收信息后重新执行四项自检
- 置信度可能升为中/高，也可能仍为低
- 仍为低则再次暂停（计入轮次上限）

### 交互轮次上限

- 最多 2 轮低置信度交互
- **2 轮后仍为低置信度**：AI 输出"无法继续"+ 状态报告，等待人给出全新指令
- 不自动回退（回退操作本身也有风险）

**2 轮后输出模板：**
```
[自检·无法继续] 经 2 轮交互后置信度仍不足，无法继续执行。

状态报告：
- 已完成的操作：{列表}
- 当前卡点：{描述}
- 低置信度项：{列表}

请给出全新指令或方向。
```

## 五、自检触发时机

### 关键节点分类

```
需要自检（写/改/发 — 产生外部影响）：
  ├─ 文件写入/修改（edit, write, patch）
  ├─ 代码执行（shell 命令）
  ├─ 发送外部请求
  └─ 删除操作

跳过自检（只读 — 无外部影响）：
  ├─ 文件读取（read）
  ├─ 搜索/grep
  ├─ 目录列表（list）
  └─ 状态查询
```

### 读→写切换触发

连续只读操作的累积可能导致理解偏差未被捕获。补充规则：

**在"从读到写的切换点"额外触发一次自检**——不管读了多少步，第一次要写之前强制过一遍四项自检。

即：自检触发 = 关键节点操作前 **或** 读→写切换点。

### 跳过规则

以下情况不触发自检：
- 纯只读操作序列中（无任何写入操作）
- 同一步骤内连续多次同类写入（如批量编辑同一文件的多个位置，首次已自检）
- 用户明确要求跳过自检（如"直接执行，不用检查"）

## 六、完整工作流

```
用户请求
  │
  ▼
AI 分析任务，开始执行
  │
  ▼
执行只读操作（读取/搜索/列表）──→ 无需自检，直接执行
  │
  ▼
遇到关键节点（写入/修改/执行/删除）
  或读→写切换点
  │
  ▼
触发四项自检
  │
  ├─ 四项全高 ──→ 高置信度 ──→ 直接执行 ──→ 继续
  │
  ├─ 1项中/低 ──→ 中置信度 ──→ 微暂停
  │                              │
  │                              ▼
  │                         自我澄清+补充说明
  │                              │
  │                              ▼
  │                         继续执行 ──→ 继续
  │
  └─ 2项及以上中/低 ──→ 低置信度 ──→ 暂停等人
                                        │
                                        ▼
                                   人做决策
                                   ├─ 继续 ──→ 人授权执行 ──→ 继续
                                   ├─ 换路径 ──→ 重新自检 ──┐
                                   └─ 补充信息 ──→ 重新自检 ─┤
                                                              │
                                              ┌───────────────┘
                                              ▼
                                         重新评估置信度
                                              │
                                    ┌─────────┼─────────┐
                                    ▼         ▼         ▼
                                   高        中        低（轮次+1）
                                   │         │         │
                                   ▼         ▼         ▼
                                直接执行  微暂停   轮次 < 2? ──是──→ 再次暂停等人
                                                     │
                                                     否
                                                     │
                                                     ▼
                                              无法继续+状态报告
```

## 七、与现有系统的整合点

### Prompt 层

自检规则作为系统提示的一部分注入 AI，让 AI 在每次关键操作前"内心过一遍"四项检查。

### 执行循环层（RapidExecutionLoop）

- 在 `tool_call_executor` 执行写入类工具前，插入自检环节
- 自检结果记录到 `LoopStep` 的 metadata 中，供审计追溯
- 低置信度暂停可复用现有 approval 机制（将自检暂停转化为一种特殊的 approval 请求）

### 前端展示层

- 微暂停的说明以特殊样式（如黄色提示条）展示在对话流中
- 低置信度暂停以 approval card 形式展示，提供三个决策按钮
- "无法继续"以醒目的红色状态展示
