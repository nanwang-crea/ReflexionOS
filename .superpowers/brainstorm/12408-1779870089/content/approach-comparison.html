对话消息编辑/分支 — 架构方案

三种实现方式的对比

A

方案 A：截断 + 重新 start_turn

新增 truncate API 删除指定消息之后的所有 turn/run/message，然后用现有 start_turn 发送编辑后的消息

优势

  • 复用现有 start_turn 流程，改动最小
  • 后端只需新增一个 truncate 端点
  • 事件溯源天然支持（追加删除事件）

劣势

  • 两步操作（截断 + 发送），中间态可能被用户看到
  • turn_index 会改变，旧 turn 被完全删除
B

方案 B：原子 edit_and_rerun API

新增 edit_and_rerun 端点，一步完成截断+编辑+重新运行。后端原子操作，客户端一次调用

优势

  • 原子操作，无中间态
  • 客户端调用简单，一个 WebSocket 消息搞定
  • 用户体验流畅

劣势

  • 后端新增逻辑较多
  • 需要处理正在运行时的冲突
C

方案 C：利用 attempt_index 多次尝试

利用 Run 已有的 attempt_index 字段，在同一 turn 内创建新 run，按 active attempt 过滤显示

优势

  • 保留历史尝试记录
  • Schema 改动最小

劣势

  • 与"覆盖式"需求矛盾 — 用户要求删除旧分支
  • 消息过滤逻辑复杂
  • over-engineering，不需要

推荐：方案 B

方案 B 最符合用户体验预期 — 一步完成编辑+重跑，无中间态闪烁。方案 A 的两步操作在快速交互时可能让用户看到短暂的"消息消失又出现"。方案 C 与覆盖式需求矛盾。
